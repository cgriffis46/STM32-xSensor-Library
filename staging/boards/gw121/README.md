# EEVblog 121GW board package

The 121GW multimeter as a board for the staged drivers. It has:
* The HY3131's register image for each range.
* The analog switch signals outside the HY3131.
* The rotary switch.
* The factory calibration, read from where the stock firmware keeps it.

**Not yet run on a meter.** Host-tested (`make -C staging/boards/gw121/test
test`), and the whole stack compiles for the meter's STM32L152ZD
(`make -C staging/cross cross`).

## Sources

Everything here about the meter comes from
[tpwrules/121gw-re](https://github.com/tpwrules/121gw-re) (its wiki, its
copy of the 121GW schematic, and its decompiled and annotated stock firmware
1.02). That project carries no license. What is used here is interoperability
data:
* register values
* pin assignments
* an EEPROM layout
* switching rules

None of the firmware's code is copied. Decide whether that is fine for your
use before this leaves the branch.

EEVblog's official repository,
[EEVblog/EEVblog-121GW](https://github.com/EEVblog/EEVblog-121GW) (GPL-3.0,
last changed December 2017), is the Bluetooth phone app (Xamarin, C#). It
has no meter firmware and no schematic. It does document the Bluetooth
protocol from the phone's side (`Controls/Multimeter/Packet121GW.cs`):

* **Meter to phone:** a packet starts with `0xF2`, then 52 ASCII hex
  digits, holding:
  * the serial number and date (BCD)
  * the mode
  * the main and sub values, with range, sign and overload
  * the bargraph
  * three status bytes
* **Phone to meter:** key presses, `0xF4` then four ASCII bytes. RANGE is
  `F4 30 31 30 31`, through SETUP `F4 30 38 30 38`. A long press starts
  `F4 38`.
* **Its mode numbers** (`eMode`: Low Z 0, DCV 1, ACV 2 … DCVA 24) are the
  stock firmware's `meter_meas_mode`, which `Gw121Routes.h`'s `StockMode`
  uses for the calibration addresses. The official app and the decompiled
  firmware agree.

This repository is MIT and the app is GPL-3.0. Firmware of ours that talks
to EEVblog's app should be written from that description of the format,
not by copying the app's code.

## How the stock firmware does things

* **Boot.** Its bootloader occupies 0x08000000..0x08006000. It checks the
  buttons, can program a firmware file from the SD card, then jumps to
  0x08006000. Firmware there is a plain image that starts with its vector
  table, and it moves VTOR to 0x08006000. Firmware of ours built for
  0x08006000 is loaded the same way, and the bootloader stays.
* **HY3131.**
  * It is bit-banged with one extra clock after a read command. That is the
    datasheet's "SPI read period", and confirms this driver's reading of it.
  * DO (PF3) is polled once per main-loop pass, not wired to an interrupt.
  * It writes one 20-register image (0x20..0x33) per range.
  * It reads all of 0x00..0x33 on every interrupt.
  * INTE: AD1IE for DC, AD1IE|CTIE for AC, CTIE for Hz and capacitance.
  * It averages 16 AD1 results per reading (8 in ohms).
* **Calibration.** It is kept in the data EEPROM. For each range, at
  `cal_factor_eeloc_tbl[mode] + 16 × range`:
  * Offset: int32, big endian, at +0.
  * Gain: uint32 / 1e6 (/ 1e5 for capacitance), big endian, at +4.
  * The firmware computes `digits = (AD1 − offset) / gain`.

## What's here

| File | |
|------|---|
| `inc/Gw121Hy3131Tables.h` | The 40 register images, generated by `tools/gen_gw121.py`. Each is checked byte for byte against the decompiled firmware's tables |
| `inc/Gw121Routes.h` | `kRoutes` for `meter::Hy3131FrontEnd`, and the calibration map. 35 ranges (generated): DC/AC V, DC/AC mV, ohms ×7, continuity, DC/AC µA, mA and A, Hz |
| `inc/Gw121Calibration.h` | `StockCalibration`: the factory calibration, read-only, from the data EEPROM (`MappedEeprom`) |
| `inc/Gw121Paths.h` | The stock firmware's switch rules (`pathLevels()`), and `Paths<TGpio>`, an `iMeterPaths` |
| `inc/Gw121RangeSwitch.h` | Rotary switch debounce (as the stock firmware: 5 equal samples, then 15 locked), position → function, MODE order |
| `inc/Gw121Bluetooth.h` | The Bluetooth protocol, so EEVblog's app works with our firmware. It encodes the 56-byte packet, decodes it back, builds it from a `meter::Reading` (`frameOf()`), and parses the phone's key and clock messages, with the echo. Written from the format, which is documented in the header |
| `inc/Gw121Glass.h` | All 160 segments of the LCD glass, by name, as {COM, SEG}. Generated by `tools/gen_gw121_glass.py` from the stock firmware's segment enums |
| `inc/Gw121Lcd.h` | The LCD as an HMI: `LcdLayout`, 54 fields bound to tags (the list is in the header). Main and sub displays, units, prefixes, AC/DC, bargraph and scale, icons. 158 of the 160 segments are on fields; the ms unit and the second amps symbol aren't used yet |
| `inc/Gw121Keys.h` | The 8 keys (PG8..PG15) and HOLD + MEM, with the stock firmware's timing. `Controller` turns keys, and the phone's key messages, into `meter.*` tag writes and beeps. RANGE (short: manual / next range, long: auto), HOLD, REL and MODE work; MIN/MAX, PEAK, MEM and SETUP beep "no" for now |
| `inc/Gw121L1Gpio.h` | The pins above, for the STM32L1 |
| `tools/gen_gw121.py` | Regenerates the two generated headers from a 121gw-re checkout |

The HY3131 goes through `BitBangSpiBlockTransport<Stm32L1GpioSpiPins>`
(`staging/itransport`). `hy3131_param_t::doLevel` reads PF3, as the stock
firmware does. `staging/cross/gw121_stack.cpp` shows the whole thing wired
together.

**Nominal scale.** Each range's nominal AD1 counts per display digit is one
meter's factory calibration (the 121gw-re calibration dump). A meter's own
EEPROM calibration replaces it. Without that, readings are close but
flagged `kUncal`.

## The LCD

The LCD controller set-up is the stock firmware's (`Stm32L1Lcd::Config`
defaults):
* 1/4 duty, 1/3 bias, internal VLCD, PS 3, DIV 0, pulse-on 4.
* Contrast CC 4. That is the stock setting 14, which it keeps at data EEPROM
  byte 26, as 12..17 meaning CC 2..7.
* Pins, AF11:
  * PA1..3, 6..10, 15
  * PB0, 1, 3..5, 8..15
  * PC0..7, 9, 10
  * PD8..15
  * PE0..3

SEG26 is not on the glass: its pin, PC8, is the SD card's D0. The glass's
26th segment line is on SEG40.

What each part of the glass shows is a tag:
* `meter.*` from `meter::MeterTags`.
* `sub.*`, `bt.on`, `batt.low`, `apo.on` and `ui.*` from the board, through
  an `xTagTable` or the PLC tag database.

Point a field at another tag to change what the meter shows. Writing
`meter.function`, `meter.range`, `meter.auto`, `meter.hold` or `meter.rel`
drives the meter, from the HMI, the shell or a PLC.

## To check on a meter

* **The rotary switch's contact order.** The stock firmware reads PG7 as Low
  Z … PG0 as mA/A, but the schematic's net labels say the reverse. The code
  follows the firmware (`kStockPinOf`). `kSchematicPinOf` is there if the
  schematic is right.
* **Whether the SYSCLK calibration (Hz) is set on real meters.** The dump has 0
  there, and the stock firmware then uses 4,915,205 Hz.
* **The LCD:**
  * Turn on every segment (`xSegmentHmi::setTestPattern`) and compare
    with the glass.
  * Show `8.8.8.8.8` and each icon in turn, to confirm the names from
    121gw-re's IDA database.
* **The HY3131 reset.** This driver writes 0x60 to R37 (from the datasheet); the
  stock firmware doesn't. Watch for trouble there first.
